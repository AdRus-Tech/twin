# Архитектура

```
Браузер (Vue 3 + three.js)
  ├─ «Смена онлайн»     → POST /api/scenario/run/, /api/scenario/compare/   модель линии
  │                       GET  /api/ml/shift/                               предупреждения ML
  │                       POST /api/ai/propose/                             совет ИИ по событию
  │                       POST /api/ai/parse-report/   {text}               сообщение с линии
  │                       GET  /api/plan/month/                             входные данные прогноза месяца
  │                       GET/POST/PATCH/DELETE /api/incidents/             журнал инцидентов
  ├─ «Аналитика»        → GET  /api/overview/?date=                         демонстрационные данные
  └─ «▶ Презентация»    — пошаговый показ поверх тех же экранов (frontend/src/components/Tour.vue)

Django + DRF (views.py — только HTTP)
  ├─ dataset.py      JSON источника → значения (source) и расчёты по ним (derived)
  ├─ simulation.py   параметры → проверка → пошаговый расчёт → результат (simulation)
  ├─ plan.py         сбои из демонстрационного журнала и их потери по модели линии → прогноз месяца
  ├─ models.py       журнал инцидентов (PostgreSQL / SQLite)
  ├─ ml/             синтетическая телеметрия, модель отказов, мониторинг смены
  └─ ai/
       contract.py   факты из результата, промпт, разбор и проверка ответа
       providers.py  DemoProvider | OpenAICompatibleProvider | SavedProvider
       service.py    расчёт → ИИ → проверка → пересчёт → объяснение
       report.py     сообщение с линии: ИИ или правила → проверенные поля события
```

Расчётный движок не знает про HTTP, Django и ИИ. AI-слой получает только готовые результаты расчёта и не влияет на числа.

## Происхождение данных

Каждое значение в API и интерфейсе относится к одному из классов:

| Класс | Метка в UI | Пример |
|---|---|---|
| значение из демонстрационных данных | `из данных` | факт 115, брак 4, план 5 500 |
| расчёт по данным | `посчитано` (пунктирная рамка) | брак 4/115 = 3,48% |
| условие пользователя | `условие` | маржа 500 тыс. ₸, рабочих дней 22 |
| результат модели линии | `модель линии` | выпуск 116, блокировка 18,2 мин |
| текст языковой модели | `ИИ`, `ИИ · сохранён`, `демо` | объяснение и мера |

## Показатели

| Показатель | Формула / смысл | Ограничение |
|---|---|---|
| Выполнение плана, % | факт / план × 100 | сверху не обрезается: 121/120 = 100,83% |
| Брак, % | брак / выпущено × 100 | порог ≤ 2%; окраска 4/115 ≈ 3,48% и 6/116 ≈ 5,17%, сварка 02.10: 3/111 ≈ 2,70% |
| Простой, мин | сумма записей журнала по оборудованию за дату | лимит 60 мин/сутки — для единицы критичного оборудования |
| План по моделям | 2 500 + 1 800 + 500 = 4 800 | общий план не менее 5 500: разница 700 показана как несогласованность данных, числа не исправляются |
| OEE | не рассчитывается | нет планового времени, идеального цикла и определения годного выпуска; показана цель ≥ 85% и причина |
| Выпуск модели | единицы, прошедшие последнюю операцию за смену | это не отгрузка годных: брак и контроль качества не моделируются |
| Блокировка / нехватка потока, мин | следующий буфер полон / входной буфер пуст | эпизоды от 1 мин дают «момент начала проблемы» |
| Эффект в тенге | машины × маржа + минуты простоя соседей / 60 × ставка часа | маржа и ставка — условия пользователя |

Параметры модели линии: циклы сварки 230 с, окраски 225 с, сборки 235 с (узкое место); накопители по 8 мест с запасом 4; смена 480 мин. Без происшествий модель даёт 122 машины при плане 120 из демонстрационных данных. На пилоте такты и накопители берутся из MES.

## Модель цепочки

**Подход:** пошаговый расчёт с шагом 1 с, детерминированный.

Почему не дискретно-событийный. На горизонте 8 ч это около 29 тыс. шагов и примерно 0,1 с расчёта. Правила записываются в 30 строк и проверяются тестами напрямую. Поминутные кадры сразу подходят для 3D и графиков. Событийный движок окупается при стохастике и большом числе ресурсов, которых в MVP нет.

**Правила:**

1. Операции идут последовательно. Между соседними операциями стоит буфер: вместимость `capacity`, начальный запас `initial`.
2. Перед первой операцией запас неограничен: склад комплектующих поток не ограничивает. После последней операции неограниченный выход.
3. Операция обрабатывает одну единицу за `cycle_s` секунд.
4. Готовую единицу операция сразу передаёт в следующий буфер. Если буфер полон, она держит единицу: это **блокировка**.
5. Если входной буфер пуст, операция стоит: это **нехватка потока**.
6. Остановка полностью замораживает операцию. Незавершённая единица остаётся внутри.
7. Внутри одной секунды операции обходятся от последней к первой. Нижний участок сначала забирает единицу, затем верхний кладёт её в освободившееся место.

**Не моделируются:** брак и его ремонт, контроль качества, партии, переналадки, транспорт, смены и перерывы, случайные отказы, маршруты по моделям автомобилей.

**Выходы:** выпуск на выходе цепочки, кадры по минутам (мгновенные уровни буферов, средние за минуту, состояния операций), максимум и минимум очереди и момент их достижения, минуты работы, блокировки, нехватки потока и остановки по операциям, эпизоды от 1 мин (момент начала проблемы), разница B − A.

**Инварианты (покрыты тестами):** `initial_wip + released = output + wip_end`; `0 ≤ очередь ≤ capacity`; сумма времени состояний равна горизонту; остановка длительностью 0 даёт тот же результат, что базовый сценарий; одинаковые параметры дают одинаковый результат.

**Несколько остановок:** кроме основной `stoppage` (её сравнивают прогноз без мер и рекомендация) можно передать `extra_stoppages` — до 8 уже случившихся в смене остановок, одинаковых в обоих расчётах. Без них ответ модели не меняется.

В живой смене общее число событий ограничено восемью, включая будущие автоматические события. Итоговый эффект считается по всей совокупности остановок: фактически выбранные решения против варианта без мер. Переносы ремонта на следующую смену также рассчитываются совместно. Суммирование эффектов отдельных карточек для итогов не используется. При ошибке расчёта эффект помечается как недоступный.

Журнал инцидентов сохраняет локальную копию и неотправленные записи. Поле `client_id` (необязательный уникальный UUID, миграция `0002`) позволяет повторять POST после потери ответа без создания дублей. Открытие журнала и ручное обновление повторяют отправку; ошибки изменения статуса и удаления не подменяют подтверждённое состояние успешным результатом.

**Валидация параметров:** разрешены только поля `stations, buffers, horizon_min, stoppage, extra_stoppages, label`. Значения целые и в диапазонах (`cycle_s` 30–3600, `capacity` 1–200, `initial` ≤ `capacity`, горизонт 30–960 мин). Нарушение даёт HTTP 400 с указанием поля.

## AI-контракт

1. Из результата расчёта собирается плоский словарь фактов `ключ → число`, например `a.assembly.starved_min`, `delta.output_units`.
2. Модель получает системные правила, задачу (`propose` или `explain`), описание цепочки, разрешённые поля с диапазонами и факты. Ответ — только JSON: `summary`, `findings[]` (`observation`, `evidence[{key, value}]`, `consequence`), `proposal`, `assumptions`, `limitations`.
3. Ответ модели считается недоверенными данными:
   - разбирается только JSON, строки обрезаются, число наблюдений ограничено;
   - каждая ссылка `evidence` сверяется с фактами: ключ должен существовать, значение — совпадать с допуском 0,05. Неподтверждённые ссылки помечаются в интерфейсе;
   - ИИ присылает до 3 предложений (`proposals`). Каждое принимается, только если поле есть в белом списке (`stoppage.duration_min` от 10 мин (не меньше) до текущей длительности, `buffers.N.capacity`, `buffers.N.initial`) и значение целое в диапазоне. Затем параметры повторно проходят общую валидацию;
   - сгенерированный код и команды не исполняются: из ответа берутся только поля схемы.
4. Каждое принятое предложение пересчитывается; лучшее (больше выпуск, затем меньше простоя соседей) становится сценарием B. В интерфейсе видны все кандидаты с результатами. Затем запрос `explain` объясняет разницу простыми словами. В промпте варианты называются A и B, но в тексте для руководителя модели велено писать «без мер» и «с рекомендацией».
5. Любая ошибка (таймаут, сеть, 401/403, 429, 5xx, не-JSON, неверная схема) превращается в статус `unavailable` или `invalid` с текстом для пользователя. Расчёт и сравнение возвращаются полностью.

**Провайдеры:**

- `demo` — правила на сервере, без сети. Помечен как демо.
- `openai_compatible` — `POST {AI_BASE_URL}/chat/completions`, `Authorization: Bearer`, `response_format: json_object` (отключается через `AI_JSON_MODE=0`), таймаут `AI_TIMEOUT_S`.
- `saved` — воспроизводит ранее сохранённый живой ответ, если хеш фактов совпадает.

Для провайдера с другим API достаточно добавить класс с методом `complete(messages, *, task, facts, fields, names) -> str` и ветку в `get_provider()`.

## Защита данных и секретов

- Ключ читается только на сервере из переменной окружения или `backend/.env`. Он не попадает во фронтенд, ответы API, логи и сохранённые ответы; тест проверяет, что ключа нет в ответе.
- Внешние вызовы невозможны без `AI_ALLOW_EXTERNAL=1`.
- Провайдеру уходят только расчётные факты синтетического сценария. Тестовые демонстрационные данные, название предприятия и журналы простоев не отправляются.
- Аналитики, трекинга и сторонних SDK нет. Шрифты системные, CDN не используется, сеть нужна только для облачного ИИ.
- Сервер слушает 127.0.0.1. Это локальный стенд, а не продуктивное развёртывание: аутентификации нет.

## 3D и интерфейс

- Модели участков и машин строятся в коде (`scene/vehicles.js`, `scene/equipment.js`) в метрах и масштабируются в единицы сцены. Кузов — лофт по сечениям, из той же сетки выделяются стёкла и пластик; фары, фонари и решётка повторяют скругление кузова. Машины меняются по стадиям: детали на поддоне → сварной кузов (голая сталь, видны проёмы) → окрашенный без стёкол → собранный. Это обобщённые обозначения, а не модели конкретного предприятия.
- Роботы участка двигаются, только пока участок работает; на сварке — искры и вспышки. Участок без кузовов («ждёт: нет кузовов») стоит пустым. Ярусы стеллажа накопителя появляются, когда кузовов больше, чем мест на полу.
- Освещение: HDR-панорама цеха (Poly Haven, CC0) для отражений, направленный свет с тенями, затенение в углах (GTAO), свечение ламп (bloom), MSAA.
- Сцена во весь экран, панели интерфейса поверх. Модуль `LineScene` на three.js не зависит от Vue. Композиция центрируется в свободной от панелей области (`setViewOffset`), дистанция камеры подбирается под ширину экрана. Качество (затенение, сглаживание) снижается автоматически, если кадры не успевают.
- Состояние операции кодируется тремя способами: цвет, положение горящей секции сигнальной колонны (сверху вниз: остановка, блокировка, нет потока, работа) и текстовая метка.
- В режиме тестовых данных сигнальные колонны выключены: исторические записи не показываются как текущее состояние.
- Без WebGL и по переключателю «2D-схема» показывается SVG-мнемосхема с той же информацией. Переключатель «Без анимации» и `prefers-reduced-motion` отключают движение.
- `dispose()` освобождает геометрию, материалы, текстуры, WebGL-контекст, ResizeObserver, слушатели и requestAnimationFrame. Проверено: после шести переключений 2D/3D на странице один canvas.

## Смена онлайн

`frontend/src/live.js` — смена 08:00–16:00 поверх тех же API. Часы смены идут в браузере (2–20 мин/с). События: внезапный сбой ABB-01 из демонстрационного журнала простоев и первые предупреждения ML демонстрационной смены (`/api/ml/shift/`). На каждое событие — `scenario/compare/`: без мер против рекомендации, с уже принятыми решениями в `extra_stoppages`. Если ремонт выходит за 16:00, остаток считается потерей следующей смены (та же модель, остановка с 0-й минуты). Решение записывается в журнал инцидентов (`POST /api/incidents/`, сразу со статусом). В карточке решения: ползунок срока ремонта (пересчёт только рекомендации), «Спросить ИИ» (`ai/propose/` с параметрами прогноза без мер; мера ИИ по сроку ремонта подставляется в рекомендацию, мера по накопителям — совет на следующие смены). Расчёт смены причинный: кадры до текущей минуты не зависят от будущих остановок, поэтому пересчёт после решения не меняет уже показанное. В конце — итог: выпуск против плана, без мер по тем же событиям и сколько машин сберегли решения.

**Сообщение с линии.** Рабочий пишет свободным текстом («на сборке порвалась цепь, минут на 40»). `POST /api/ai/parse-report/` разбирает его в участок, оборудование, причину и срок ремонта. Если подключена языковая модель, она возвращает JSON; каждое поле проверяется (участок — только из списка, срок — целое 1–480 мин), неверное заменяется разбором по ключевым словам. Без модели и при любой ошибке работает разбор по правилам. Понятое сообщение сразу становится событием смены с карточкой решения; если участок или срок не понятны, открывается форма события с заполненными полями.

**Ввод руководителем.** «＋ Событие» — форма: участок, время, срок ремонта, причина; событие ставится в текущую минуту смены.

## План месяца

`GET /api/plan/month/` (`plan.py`) отдаёт входные данные: цель 5 500 и 2 смены в день из демонстрационных данных, выпуск смены без происшествий (122), частоту сбоев из журнала простоев (4 записи за 2 дня ≈ 1 на смену) и потери машин от каждого сбоя без мер и с мерой — модель линии, среднее по пяти моментам смены. Прогноз считает `frontend/src/plan.js`: Монте-Карло на 3 000 месяцев (число сбоев за смену — Пуассон, сбой — случайная запись журнала), генератор с фиксированным зерном. Результат: среднее и 80% интервал без мер и с решениями (5 166 и 5 313 при 22 рабочих днях), мощность без единого сбоя (5 368) и что нужно для 5 500 (+2 смены или такт сборки ≤ 228 с). План по моделям (Onix 2 500, Cobalt 1 800, JAC J7 500) раскладывается по дням месяца при прогнозном темпе; 700 машин без модели показаны отдельно.

## Режим презентации

`Tour.vue` — 16 шагов в 6 главах. Каждый шаг сам переключает экран, ведёт смену (старт, ускорение до события, решение, сообщение с линии, автопилот до конца смены) и подсвечивает блок; текст карточки берёт числа из текущего расчёта. Шаги, двигающие смену, выполняются один раз — при возврате назад показывается только подсказка. Клавиши: → / пробел / PageDown, ←, F — полный экран, Esc — выход.

## Хранение и развёртывание

- **База данных:** журнал инцидентов (`twin.models.Incident`) — PostgreSQL в Docker или SQLite при локальном запуске (выбор по `DATABASE_URL`). Тестовые демонстрационные данные остаются в `backend/twin/data/source_dataset.json` без изменений, сценарии считаются на лету и в базу не пишутся.
- **API журнала:** `GET/POST /api/incidents/`, `PATCH/DELETE /api/incidents/<номер>/`. Сервер проверяет поля и принимает от клиента только последствия из белого списка (`lossCars`, `idleMin`, `output`). Если API недоступен, интерфейс хранит журнал в браузере.
- **Docker:** `Dockerfile` собирает фронтенд в Node и запускает Django под gunicorn в `python:3.12-slim` от непривилегированного пользователя; `docker-compose.yml` добавляет `postgres:16-alpine` с проверкой готовности и томом данных. Порт базы наружу не открыт.

## Прогноз отказов (ML)

- `backend/twin/ml/telemetry.py` — синтетическая телеметрия и демонстрационная смена (обрыв цепи Конвейера-03 в 13:30, замена фильтра Камеры-02 около 15:50).
- `backend/twin/ml/model.py` — признаки окна 60 мин, логистическая регрессия (Adam, L2), метрики: ROC-AUC, предупреждённые отказы, упреждение, ложные на 100 ч; выбор порога на валидации.
- `manage.py train_failure_model` — обучение на трёх историях, порог на четвёртой, метрики на пятой; сравнение с простым правилом; `model.json` и `docs/ML_REPORT.md`.
- `GET /api/ml/shift/` — риск по оборудованию на демонстрационной смене с шагом 5 мин, предупреждения с объяснением, метрики проверки. Интерфейс превращает предупреждение в событие для модели линии: без мер — авария (ремонт из журнала), рекомендация — замена заранее; событие пишется в журнал инцидентов с источником «прогноз ML».
